## §0 前提指示（作業規約）

### 0.1 役割と進め方

- あなたは実装担当である。設計判断は本書に従い、本書にない判断が必要になったら
  推測で進めず、その判断点だけを切り出して §11 の未決事項として報告し、指示を待つこと。
- **1 Phase = 1 ブランチ = 1 PR（または 1 コミット群）**。複数 Phase を同時に混ぜない。
  特に Phase 2（ロック統一）・Phase 3（Undo 整合性）・Phase 6（God Class 分割）は
  いずれも広範囲に触るため、絶対に同時に行わない。
- 各 Phase の完了条件は、当該 Phase 本文の「完了判定」節と、§9.1（全 Phase 必須）および
  当該 Phase に該当する §9.2 を満たすこと。`pytest` が通るだけでは完了としない。
  **例外（Phase 0 のみ）**: Phase 0 は記録フェーズのため、§9.1 は「実施と記録」をもって足り、
  通過は要しない（ベースラインが赤でも Phase 0 は完了できる）。
- 作業開始前に必ず読むもの:
  本書、総括ファイル、既存の改修仕様書（`~/workspace/ImageTaggerGUI-improvement-spec.md`）、
  一時改修仕様書（`~/workspace/ImageTaggerGUI-temporary-improvement-spec.md`）。
  ただし仕様と実装が食い違う箇所は実コードを正とし、ズレは Phase 0 の台帳に記録する。

### 0.2 絶対に守ること

- **ユーザーの実データは検証で壊さない**: 実 `config.ini`、実フォルダの `.txt` 群、
  keyring の実エントリ、実 `vlm_connections.json` / `vlm_profiles.json` を
  テストや検証で上書き・削除しない。検証はコピーかテンポラリディレクトリで行う。
  この規約自体が Phase 1 の対象（R11-1〜R11-3）でもある。
- **部分成功を成功と偽らない**: 一括処理・Undo・保存・DL のいずれでも、
  一部が失敗した結果を「全成功」として記録・表示しない（§3 の NFR-10）。
  失敗した対象と件数を、従来の表示粒度を下回らない形で残す。
- **黙ってデータを失わない**: 読み込めなかった既存データを「空だった」ものとして
  上書きしない。読めない場合は書かないか、書く前に原本を保全する（NFR-11）。
- **応答・コメントは日本語**。識別子・コミットメッセージの英語サマリ部分は英語でよい。

### 0.3 やらないこと（スコープ外、CUT リストは §6）

新機能追加・UI レイアウト変更・対応モデル追加は「二次改修」に含めない。
二次改修とは「既に作られた機能が、宙ぶらりんな中間状態なく、壊れずに動く」状態にすることである。
例外は §6 で個別に判断する機能候補（先行配布分の Q 等）のみで、
Phase 0 の判断記録なしに実装へ進んではならない。

### 1.2 B に関する訂正（確定事項。旧方針は使わない）

- 旧方針「ファイル名は単一コンポーネントのみ許可」は**誤りであり撤回する**。
  Florence-2 の `model_config.json` は `network.files` のキーに
  `onnx/vision_encoder_quantized.onnx` 等のサブディレクトリ付き相対パスを正規に使う
  （同梱モデル中で Florence だけ）。
- 正しい方針は「**安全な相対パス**」の許可である: 通常のパス区切りでつながった相対パスのみ許可し、
  絶対パス・ドライブレター・`..` コンポーネント・空コンポーネントは拒否する。
  書き込み先は resolve したうえで `model_dir` 配下に収まることを検証する。
- 同じ経路の潜在問題も B に含む: `_download_from_manifest()` はポインター URL を
  `url.replace("/resolve/main/", "/raw/main/")` で機械的に導出している。
  同梱 30 URL は全て `/resolve/main/` を含むため現状は安全だが、置換が効かない URL では
  `get_model_info_from_pointer()` が実ファイル自体を（stream なしで）丸ごと読みに行き、
  巨大ファイルでメモリを圧迫しうる。置換が効いた場合だけポインター取得すること（Phase 7。置換が効かない場合の DL の扱いは REQ-7.4 で定義する）。

### 1.3 一時改修との実施順序（2026-11-27 決定）

段取りは次の 3 段とする。第 1 段（反映）と第 2 段（本書の改修）は 2026-11-28 に完了し、
第 3 段のレビューループも同日に完了した（独立レビュー2系統・全8周、新規指摘は第1〜6周で計42件を反映、誤検出1件を棄却、
技術正確性系統は第4〜8周、整合性系統は第7・8周で新規指摘ゼロが2周連続し収束条件を満たした）。
本書は確定版である。

1. **一時改修を実際に反映させる**（一時改修仕様書の実装とマージを先に完了させる）
   ― **完了（2026-11-28 確認）**: 一時改修仕様書の Phase 1〜4 と、77 件側仕様書の
   Phase A／E／G が PR #31〜#37 で実装・マージされ、PR #38 のレビュー指摘 10 件への
   対応（PR #39）までが `dev` ブランチへ入った。新しいベースラインは §2.1 のとおり。
   本書の改修（第 2 段）はこの状態を基準に行った（§2.4）。77 件側の残り Phase
   B／C／D／F／H も 2026-11-28 に dev へ取り込み済み（§2.1 の新しいベースライン）
2. **それを踏まえた改修を本書に行う**: マージ後の実コードを基準に、本書の「現状」節・
   行番号・前提（原子書き込みの共通部品、バッチループ共通化後の構造、NFR の差分等）を
   実態へ合わせて更新する。本改修で行ったのは §2.4 のスポット確認までであり、129 件全件の台帳化（REQ-0.1）は未実施のまま Phase 0 の作業として残る
3. **その後にレビューループを行う**: 更新後の本書を対象に、独立レビューを
   新規指摘ゼロが 2 周連続するまで回し、そこで初めて本書を確定とする

- 原則として、**一時改修仕様書の全 Phase がマージされた後に本書の実装 Phase へ着手する**。
  一時改修はコア／データ層（担当 77 件を含む）を触り、本書の Phase 2・3・6 と
  同一ファイル・同一関数で衝突するためである。
- 例外は Phase 0（コード変更なし）と、Phase 0 の衝突確認で「同一箇所に触れない」と
  記録できた Phase・PR のみとする。先行させる場合はその根拠を台帳に残す。
- 一時改修側の要件（REQ 番号体系はあちらの正本）を本書で書き換えない。
  本書の修正が一時改修の前提（例: 原子書き込みの共通部品、バッチループ共通化後の構造）を
  使う場合は、その前提が入った後のコードを基準に「現状」節を Phase 0 で更新する。

## §4 切り分けマトリクス — 129 件の Phase 配置の根拠

129 件は次の 3 区分のいずれかに属し、付録 A に全件の区分と Phase を記録する。

### 区分 1: 分割（Phase 6）前に直す — 状態管理系

Phase 2（ロック）、Phase 3（Undo）、Phase 4（データ喪失・不整合）、Phase 5 のうち実行中状態に関するもの。
理由: MainWindow の切り出しは「移すだけ」が原則であり、状態の意味論（何をロックするか、
Undo の成否をどう数えるか、誰が状態を持つか）が固まっていない状態で移すと、
同じ欠陥を新クラスへ移植することになり、二度手間と事故の温床になる。

### 区分 2: 分割と同時にしか直せない

Phase 6 の各切り出しの内部に閉じる指摘（R1-8、R6-2、R8-1、R8-2 のスレッド寿命・終了経路、
R7-12、R19-5 のデッドコード／デッドフィールド）。
理由: 対象コード自体が切り出しで移動するため、先に単独で直すと切り出し時に再度触ることになる。
これらは Phase 6 の該当 REQ に抱き合わせ、単独 PR では着手しない。

### 区分 3: 分割と独立 — 先行・並行可

Phase 1（テスト基盤）、Phase 7（B）、Phase 8（個別指摘）、Phase 9（C／D／配布）と、
Phase 5 のうちダイアログ側のもの。
理由: 対象が MainWindow の責務分割と重ならない。ただし §1.3 の実施順序
（一時改修のマージが先）は区分 3 でも変わらない。

なお Phase 5 は区分 1 と 3 の混在であり、内訳は次のとおり（付録 A の区分欄もこれに一致する）:
区分 1 は実行中状態に関する R8-3、R7-6、R9-3 の 3 件（REQ-5.4、REQ-5.5 が受け皿）。
残りの 20 件は区分 3（ダイアログの保存・寿命・表示の整合）。Phase 5 を 1 つの Phase として
まとめるのは、対象コード（設定ダイアログ群と設定保存経路）が共通するためであり、
実施順序は Phase 内で区分 1 の REQ を先に行う。

### 11.1 決定内容と実装上の帰結

Phase 0 の実測・選択肢は付録 C.5 に残す。以下は決定後の実装方針であり、
各 Phase はこの方針に従う（決定は 2026-11-28 に利用者の承認を得た）。

**U-1（処理中は受理しない）**
切替経路は `dropEvent`（main_window L1497）／`browse_folder`（L1470）／
`_on_input_path_changed`（L1478）の 3 つで、いずれも `_handle_folder_drop`（L1459）に
集約されている。その先頭で処理中を見て弾き、debug log に 1 行残す。保留パスは持たない
（NFR-9）。画像 1 枚の D&D も同じ経路なので処理中は効かないが、`image_list` も無効なので
一貫する。新規ユーザー文字列は不要（ログのみ、NFR-5）。

**U-2（3 値化し、部分成功は履歴を進める）**
`undo_manager` に `UndoResult`（FULL／PARTIAL／FAILED）を置き、`CompositeUndoAction` と
一括アクション群の戻り値をこれにする（外部互換のため `UndoManager.undo/redo -> bool` は
畳んで維持する）。遷移は次のとおり。

- FULL → 反対スタックへ移す
- PARTIAL → 反対スタックへ進める。失敗した対象パスと件数を error_log と GUI ログへ列挙する
  （NFR-10）。「戻せなかった分は戻らない」ことを利用者に示す
- FAILED → アクションを元のスタックへ戻す（一時的な失敗の再試行を許す）
- FAILED のうち恒久失敗（対象 .txt と親フォルダの消失、権限拒否）は履歴から外し、
  ログに残す（R11-11 のデッドロックを解消する）

`any(...)`／`success_count > 0` を成功判定に使わない（残存箇所は §2.4 の Phase B 行）。

**U-3（disk からの再読込）**
`model_status_changed` を受ける薄いスロットで `load_config()` → `load_settings()` を通し、
`self.settings.model.verified_models` を差し替えてから
`_check_model_status_and_update_ui()` を呼ぶ。シグナル形状（KEEP-2）は変えない。
再読込はシグナル経由に限定し、通常の UI 更新では disk を読まない（NFR-4）。
既存前例は `_on_download_finished`（main_window L2028）。

**U-4（閉じたら破棄）**
`ImageViewerDialog` は閉じたら破棄する。`finished` ハンドラで `deleteLater()` してから
参照を None にし、次回は再生成する（`WA_DeleteOnClose` ではなく `finished` 起点にするのは、
Python 参照と C++ 破棄の順序を自分で決めるため）。ASK の `QMessageBox` は `exec()` の後に
`deleteLater()` する。

観測差が出ない根拠: グリッド側は画像切替のたび `setPixmap()` → `reset_view()` でズーム／パンが
初期化され、main 側のナビゲーションモードはズームを使わず、`setGeometry` も毎回計算している。
インスタンス固有の持ち越し状態は無い（NFR-8）。

**U-5（既定は exe 隣、書き込み不可時だけリダイレクト）**
起動時に `config.ini` の置き場所へ一時ファイルを作って消す probe を行い、不可なら設定・ログ・
VLM JSON・`gpu_runtime/` を `%LOCALAPPDATA%\ImageTaggerGUI` へ向ける。`models/`（数 GB）は
リダイレクトせず、DL 開始時に「保存先が書き込み不可」を明示エラーにする（黙って False を
返さない、REQ-9.4）。既存データの移行はしない。どちらを使っているかを起動ログ 1 行と About に
出し、サポート時の曖昧さを消す。zip 配布（exe 隣が書き込み可）を既定とし、Program Files 配下は
README で非推奨とする。

**U-6（terminate() を残さない）**
`reload_tags_only`（main_window L785）と `closeEvent`（L1370）の 2 箇所を detach 方式へ
統一する。`reload_tags_only` は旧 `TagLoader` の `tags_loaded` に加えて `finished` も
disconnect する（R8-1 と同時に直す）。旧ローダは読み取り専用なので自然終了を待って害はなく、
シグナルを切ればエイリアシングも起きない。待機は既存の `wait_for_detached_threads()` を使い、
タイムアウト値（5000ms）は変えない（REQ-6.5）。`terminate()` が 0 箇所になったことを
テストで固定する。

**U-7（CI は前提チェックまで）**
CI は `ruff`／`pyright`／`pytest`（`QT_QPA_PLATFORM=offscreen`）に加えて前提チェックを行う。
前提チェックは PyInstaller を入れず、pytest の 1 テストとして `gpu_components.json` の
スキーマ検証、`ImageTaggerGUI.spec` が要求するデータの存在確認、`lang/*.ini` のパリティを行う。
spec の `SystemExit` を CI で再現するのではなく、同じ条件をテストで固定する。フルビルドは
リリース担当が手元 Windows で行う（PyInstaller はどの requirements にも未宣言。R6-7）。

**U-8（割り込み順位）**
(1) 進行中の Phase は必ず閉じる（Phase 混在禁止、§0.1）。(2) 割り込みは次 Phase の着手前に
限る。(3) 例外として、データ喪失・秘密情報の露出・実ユーザーデータ破壊に該当する E 項目は、
現在 Phase の PR 提出直後に即時割り込みする。(4) 割り込みは Phase 番号を振らず `E-n` の枝番で
管理し、付録 A／B へ追記する。

**U-9（resolve 先の配下判定のみ）**
`model_dir` を `resolve()` し、`(model_dir / file_name).resolve()` が配下に収まることを
検証する。書き込み直前に親ディレクトリも resolve して配下判定する。リンク自体は拒否しない
（Windows の junction は管理者権限不要で、`models/` を別ドライブへ置く正規運用がある）。
脱出リンクは resolve で外を指すため、配下判定で弾ける。

**U-10（`.bak` 退避付き置換＋条件付き復元）**
`_mirror_capi_files` は `os.replace` の前に既存 `dst` を `.bak` へ退避し、manifest に
`backed_up` を記録する。復元は `uninstall()` と修復導線で行い、**現 `dst` が我々のコピーと
一致する場合だけ**戻す（他者が上書きしていたら触らない）。この「一致するときだけ戻す」は
REQ-3.4（R13-6）と同じ原則で、判断を 1 つに揃える。

Phase 0 の実測（`any()` の全箇所、書き込み 7 系統、terminate 2 箇所、DLL 上書き手順等）は
付録 C.5 に残す。U-8 は発生時に本節へ追記する。
